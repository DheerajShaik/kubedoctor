# Pre-implementation design review

Independent review of FROZEN-v1.0 and the proposed Go/client-go package boundaries. This pass evaluated the design before implementation. Release evidence belongs in [VALIDATION.md](VALIDATION.md).

## Material findings

1. **Coverage needs to survive partial collection.** Record the state of each source and scope, including denied, unavailable, failed, incomplete and inapplicable. Preserve the usable items from earlier pages and retain the failed state. Positive conclusions can use those items when their evidence is sufficient. Findings that rely on absence require successful collection of the relevant source and scope. Keep metrics and uninspected Secret contents visible as capability limits. Explicitly classify which sources are required under each scope. A required collection failure takes precedence over the failure threshold for exit status. Severity filtering should affect presentation only, so filtering a finding cannot change its exit status.
2. **Keep namespace dependencies narrow.** Collect namespace objects through namespaced list paths. Read only hosting nodes named by observed Pods and StorageClasses named by claims. Use a named or tightly scoped query for DNS dependencies in `kube-system` and explain how the default fits managed or nonstandard DNS. Distinguish authenticated HTTP 403 from API unavailability, object deletion and a successfully empty list. A 403 never authorizes a broader list or a compatibility fallback. Prefer targeted group/version discovery and bounded pagination to a broad discovery walk. Bound pages, item count, concurrency and elapsed time, including repeated continuation tokens and stalled API requests.
3. **Use a narrow data boundary and a reviewed read-only request surface.** Keep Kubernetes API calls explicit and typed. Do not expose a generic requester through the engine or MCP. The normalized snapshot and report should admit only needed resource identifiers, timestamps, counters, reference metadata and defined evidence fields. Process a configuration event message transiently and emit only the recognized fact tied to a matching reference. Do not reflect free-form event, termination, status or API error messages even when requesting verbose output. Keep Secret objects and application logs outside the collector. Existing kubeconfig credential helpers are operator-controlled startup authentication. Keep any inputs that can change the selected credentials, paths, commands or API endpoint out of the MCP tool schema. Assert the actual HTTP methods and routes, including forbidden subresources, and ensure a seeded event never becomes a command, a network target or output.
4. **Make correlation and time explicit.** Establish an observation time once per scan and pass it into pure rules. Match Kubernetes Events by involved-object UID when available. Match names only with sufficient scope, object kind and lifetime evidence when a UID is unavailable. Use event series freshness and distinguish a pod's most recent observed state from older evidence on a previous instance. Group supplemental scheduling, event and owner evidence around the actionable symptom while retaining independently actionable findings. Keep output order stable after concurrent collection. A recently recovered termination is historical even when it warrants an advisory.
5. **Guard diagnoses that depend on controllers.** Use controller generation and rollout progress. Stale deployment, DaemonSet and PDB observations become inconclusive. Teach tests about new rollouts, paused deployments, deployment and DaemonSet zero targets, Jobs that completed successfully, and waiting PVCs backed by `WaitForFirstConsumer`. A scheduling event can establish a reported symptom or reason when correlated. The analyzer should avoid filling gaps by inferring taints, capacity or affinity from the pending phase alone.
6. **Give backends a precise definition.** Prefer and aggregate all relevant EndpointSlices, checking service identity, ports and endpoint conditions. Handle nil `ready` according to API semantics, distinguish `serving` with `terminating`, and account for `publishNotReadyAddresses`. An otherwise usable terminating backend can still serve during draining. Separate a demonstrably mismatched selector or port from an empty result with incomplete visibility. Headless and selectorless Services can use valid DNS or manually managed endpoints, ExternalName does not use Pod backends, and a matching scaled-to-zero workload can explain absent backends. If a legacy Endpoints fallback is implemented, limit it to confirmed EndpointSlice API unavailability and report its reduced fidelity.
7. **Limit claims from static networking and single-sample metrics.** NetworkPolicies select pods within the policy namespace, can default `policyTypes`, and combine additively. Cross-namespace selection and actual enforcement may be unknown. State which pods and directions appear selected, with uncertainty where other policy or runtime context is missing. DNS component readiness is infrastructure evidence. An unavailable or nonstandard DNS installation leaves diagnostic visibility limited. A single Metrics API sample is time-stamped current usage with its reported window and units. It supports observed usage and request/limit comparisons under suitable visibility. Historical percentiles and sizing are outside this release.
8. **Bound the MCP adapter independently.** Start with a fixed context and explicit namespace allowlist and separate cluster enablement. Validate tool schemas and reject unrecognized parameters. Ensure every request has an upper time bound and the server has an upper concurrency bound across requests. Size-limit serialized responses and return an explicit truncation or operational error with bounded available evidence. Protocol stdout must carry only MCP frames. Exercise unauthorized scopes, invalid inputs, cancellation, output limits, and normal stdio initialization and tool calls through a separate SDK client process.

## Release evidence to check

- Require a test table that includes observed failure, supported healthy cases and insufficient visibility for each category. Very specific invariants include a missing Secret event remaining distinct from CrashLoopBackOff, exit 137 alone staying inconclusive for OOM, arbitrary event strings never reaching reports, and zero allowed PDB disruptions being an eviction constraint.
- Prove required permissions and product behavior with sanctioned test credentials and fixtures. Exercise kubeconfig/context resolution against temporary files and read-only routes against a recording test server. Exercise the actual binary through `kubectl plugin list` and `kubectl doctor` via a temporary PATH.
- Prove Kubernetes compatibility on the specific disposable-cluster version or versions named in the support policy. Local Docker access, workflow configuration and external review requests are prerequisites. The validation record needs the observed cluster run, CI and external review results for the relevant revision before an authorized merge.
- Keep compatibility, allowed operations and output schema in user documentation. A build for a foreign GOOS/GOARCH establishes cross-compilation. Record any tested runtime platforms separately.

The package boundaries are suitable if the implementation keeps scope, visibility, identity and data minimization explicit. Recheck these findings against the implementation and mark the supporting tests before merging.
