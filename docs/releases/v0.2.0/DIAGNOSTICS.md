# Expanded diagnostics

The additional checks run over the same normalized Kubernetes observations in live collection and offline replay. The existing default JSON report remains version 1. Additional check and source IDs are additive. The six new namespaced inventories and the NodeLocal DNSCache reads are optional coverage. A denied or unavailable new source produces an inconclusive or skipped check as appropriate and excludes unsupported conclusions. It does not independently cause legacy scan exit 2. Observed warning findings can meet the configured failure threshold. See the [release charter](RELEASE_CHARTER.md) and the [acceptance matrix](ACCEPTANCE.md).

| Check ID | Evidence and finding criteria | Expected states and limitations |
| --- | --- | --- |
| `statefulset-rollout` | Inspect current-generation desired, ready, available, and updated counts. Link an owned ordinal by Pod owner UID and name. Compare its required PVC references with named templates and visible claims. A shortfall plus an observed Pod startup failure, lost claim, or absent referenced claim is a warning. After the initial grace period, a remaining initial-generation shortfall is a warning. A later shortfall without measured rollout timing remains an informational observation with incomplete timing. | Scale-to-zero, OnDelete updates, partitioned updates below their threshold, and orderly convergence are expected. The initial grace is the greater of five minutes and `minReadySeconds`. Delayed claim binding without an assigned consumer is expected. Stale controller status, missing required inventory, or unknown binding mode limits the conclusion. The supported controller uses a replica index relative to the start ordinal when applying a rolling partition. |
| `job-execution` | Read Job conditions and execution counts. Recent `Failed=True` and `FailureTarget=True` are warnings. Report the controller's recognized reason and transition time. An observed active execution beyond the configured deadline is a warning awaiting final controller status. Earlier terminal failures and nonterminal failed attempts are informational. | Completed and success-criteria-met Jobs are expected. Controller or spec suspension and zero parallelism suppress active-failure inference. The number of failed Pods is separate from the controller's retry accounting. An older Job lacking an observed start or outcome is inconclusive. |
| `cronjob-scheduling` | Capture suspension, concurrency policy, last schedule and success timestamps, and recent classified schedule events. Correlate recent failed Job outcomes using `CronJob` controller UID and suppress superseded failures after a captured success. | Suspension and `Forbid` overlap are informational. A subsequent observed schedule supersedes an earlier scheduling warning. The rule makes no prediction from the raw schedule and needs child Jobs and events for full visibility. |
| `hpa-scaling` | Inspect HPA scaling conditions and `apps/v1` Deployment, ReplicaSet, or StatefulSet references. Confirm missing supported targets only with complete target inventory. Observe metric-driven scaling failures and replica bounds. For utilization-based CPU and memory, identify verified Ready target-owned Pods with missing requests, including restartable init containers and Pod-level requests where relevant. | Replica limits and static missing requests are informational. `ScalingDisabled` can be expected. The upstream HPA can omit both generation fields. Recent controller conditions are then informational, or warnings if a recent same-UID controller event corroborates the reported failure. The check remains inconclusive about status association with the current spec. Explicit generation mismatches suppress condition diagnoses. Ownership does not establish exact membership of every HPA metric sample. Unrecognized scale targets do not establish absence. |
| `namespace-admission` | Compare bounded quota hard and usage amounts only when observed hard values agree with the current spec. A saturated quota is informational. Classify selected recent `FailedCreate` API rejections and corroborate them with an observed matching named quota or compatible LimitRange. | A matching constraint does not guarantee the same policy revision applied at event time. A LimitRange rejection does not include a stable LimitRange identity, so the rule reports compatible candidates. Quota and LimitRange evidence concerns admission before scheduling. Arbitrary rejection text is excluded. |
| `rollout-probes` | Match a bounded, classified kubelet event to a declared startup, readiness, or liveness probe on the same Pod and container. Corroborate it with current readiness and container timing. A current UID-linked controller availability shortfall raises severity. | Ready, recovered, old, or superseded Pod identities do not create an active probe finding. Current probe evidence uses a fifteen-minute event window. Probe command, HTTP path, headers, and arbitrary event text are excluded. |
| `service-endpoint-identity` | Require a controller-managed IPv4 or IPv6 EndpointSlice and matching Service owner UID. Detect a non-terminating endpoint that still names a previous UID after a replacement Pod matching the Service selector has existed at least one minute. | Informational static evidence only. Selectorless, ExternalName, custom-managed, terminating, and newly replaced backends receive no stale-identity alert from this rule. The legacy Endpoints fallback provides no coverage for this check. |
| `node-local-dns` | Read the conventional `kube-system/node-local-dns` DaemonSet and its `k8s-app=node-local-dns` Pods. In a namespace scan, correlate owned cache Pods with observed workload hosting nodes. Cluster scans can report a mature DaemonSet's Ready shortfall. | A custom name or deployment style is outside this arrangement. Missing visibility or unknown readiness is inconclusive. Conventional DNS and NodeLocal DNSCache readiness describe infrastructure and cannot establish resolution from any workload. |
| `networkpolicy-named-ports` | Compare named ingress ports and protocols with declared ports on Pods selected in the same namespace. Report only when none of the observed selected Pods declares the name and protocol. | Ingress rules and policies combine additively. The check needs complete Pod visibility and uses a deterministic budget of 250,000 selector or port evaluations. An informational finding cannot establish a traffic denial, CNI enforcement, or named egress resolution. |

## Collection, provenance, and permissions

New inventories use the stable `apps/v1`, `batch/v1`, `autoscaling/v2`, and core typed clients. The collector allows at most four source workers, 200 items per page, 25 pages and 5,000 items per source, three request attempts, and 32 MiB decoded per response. Optional expansion uses up to four seconds or half the remaining operation deadline, whichever is smaller. Each recorded source interval spans the attempted pages or one named read. Capture start and finish span the full operation. Requests can overlap and a resource can change between reads.

Cluster capture can derive strong comparison provenance from a named `kube-system` Namespace GET. Namespace capture uses the requested namespace's existing authorized UID lookup and makes no extra cluster-identity request. The capture retains a scoped SHA-256 digest and its method. The digest is a comparison identifier, and it changes if the namespace is recreated. A denied or invalid identity lookup leaves provenance unavailable. Legacy scans do not request this cluster marker. [RBAC examples](../../../rbac/README.md)

Collection retains allowlisted workload identities, owner and target references, lifecycle timestamps, statuses, resource names and quota figures, probe categories, and controller observations. Runtime IDs used for historical joins require a bounded lowercase runtime prefix and 64 lowercase hexadecimal digits. The collector discards literal environment values, probe handlers, annotations outside an explicit rule, and free-form event or condition messages. Named networking checks retain the declared port and protocol without preserving peer addresses. Inspect the [bundle contract](BUNDLE.md) for persistence limits and handling.

## Verification

`go test ./internal/analyze ./internal/collect` runs deterministic fixtures for all the checks above, including readiness, replacement UIDs, policy coverage gaps, and expected batch and storage states. Collector tests exercise typed loopback HTTP, redaction, exact namespace and named routes, unavailable APIs, denied access, and capture-only identity. `go test -race ./internal/analyze ./internal/collect` exercises the source workers and timing records.

`go test -run '^$' -bench '^BenchmarkCollection250Pods$' -benchtime=10x ./internal/collect` measures collection alone against a loopback typed HTTP fixture with a 200-Pod page and a 50-Pod final page. It records request count, latency, and allocations with a fresh client per scan. This benchmark excludes kubeconfig resolution, analysis, serialization, and remote cluster latency.

Ten loopback runs on Linux amd64 with Go 1.27.4, an AMD EPYC 9V74 processor, and `GOMAXPROCS=4` averaged 15.25 ms, 28 HTTP requests, 3,756,864 allocated bytes, and 13,345 allocations per capture.
